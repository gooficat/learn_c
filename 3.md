### How Apps Work

In the first chapter, we touched on how a typical application works. For an application to run on an operating system, it has to be loaded into an isolated place in memory, where it is then given short periods of time to execute its code, then the OS takes back control for a while before passing it back at the saved space.

We also briefly mentioned how the app can interact with outside code. The two mechanisms are through system-calls, and dynamic libraries.

However we have some problems here. What if our code contains a non-relative address? For example, our fibonacci code from earlier stored some variables at the bottom of the program. We accessed those with their address when we did MOV operations to fetch and change their values.

Let's look at that code in terms of the Assembly language. This is a special way of representing machine code in a human-readable way.


```
loop:
	mov eax, [fib]
	add eax, [prev] 
	mov [now], eax
	mov eax, [fib]
	mov [prev], eax
	mov eax, [now]
	mov [fib], eax
	jmp loop

fib:
	dd 1
prev:
	dd 0
now:
	dd 0
```

The first part of this code is a label `loop`. This lets us mark a location in the code to use as a parameter for jumps. It's entirely a language concept and doesn't exist in the outputted byte code.

The next part is an instruction. It is a ``mov`` operation. On x86, load and store are part of the same instruction, ``mov``. Whether it is a load or store just depends on which direction you move the data. This one loads the value at the label ``fib`` onto ``eax``.

``eax`` is a general-purpose register on x86 computers. It has no pre-defined use and can be used for many operations.

The square braces around ``fib`` indicate that we are loading the value located at the address, not the address itself.

The next instruction is ``add``. On x86 we can operate on some values from memory without loading it first, but at least one parameter must be a register.

There are a number "mov" instructions, followed by an unconditional jump operation back to the ``loop`` label.

Then, there are the 3 labels for our variables, followed by a pseudo-instruction, ``dd``. Also known as a directive, this is something that does not translate to an instruction, and is defined by the *Assembler* itself. This one places a double-word, which is 4 bytes, with a specified value (in this case the values are 1, 0, and 0).

Now that we understand this piece of code somewhat, we can look at the problem. The translation for this instruction:

``mov eax, [fib]``

Is this:

``8B, 04, 25, 33, 00, 00, 00``

`8B`, `04`, `25`, is the op-code. This defines which instruction it is and which register it uses.

The important part is

``33, 00, 00, 00``

This is the number 51 in hexadecimal bytes, in little-endian byte order.

But if our OS loads this app at some address that isnt 0, like ``0x81000000`` for example, the jump will map to an incorrect location! We amend this by including extra information in our executable file that tells the application-loader where all the absolute addresses are, so it can patch in the new values.

Let's look at an older executable format called A.out. This format predates EXE and ELF and is much simpler.

Before we start, it's important to understand what "sections" are. Basically, our code is split up into logical sections with different permissions attached to them. The OS can give them different permissions.

The ``code`` (also known as ``text``) section is executable, and usually read-only. This is where the code goes!
The ``data`` section is readable, writable, but not executable.
The ``bss`` section contains uninitialized data. It doesn't need to exist in the executable because it has no designated value, only a size.
The ``rodata`` (read-only) section is readable only, with no other permissions allowed. Slightly less common than the other 3.

Another important thing to understand is that an executable file can have symbols associated with it. These symbols are used for accessing functions from dynamic libraries. For example, a library might have a function to display to the screen. Perhaps it is called `print`. When writing our program, we need to write a call to this function, but we don't know whereabouts in memory it will be! Instead, we declare that this symbol is external, and the symbol can be listed in the executable file as a symbol that must be imported.

---

The A.out file starts with a header. The fields of the header and the space they occupy are as follows:

Bytes | Name | Purpose
--- | --- | ---
2 | a_magic | Tells us that this is a valid A.out file, and which type it is.
4 | a_text | Tells us how long the "text" section of the file is in bytes
4 | a_data | Tells us how long the "data" section of the file is in bytes
4 | a_bss | Tells us how long the "bss" section of the file is in bytes
4 | a_syms | Tells us the size of the table containing symbols in bytes
4 | a_entry | Tells us the byte address of the *entry point* of the program is. This is where execution starts, where the instruction pointer goes first. The entry point is inside the text section.
4 | a_trsize | Tells us the size of the table containing relocations inside the ``text`` section in bytes
4 | a_drsize | Tells us the size of the table containing relocations inside the ``data`` section in bytes

After this is the actual sections (but not BSS! That one only exists at runtime).

This is followed by the tables, starting with text, then data. These are just lists of byte locations, each being the length of the address size of the current mode of operation (i.e. it will be 8 bytes for a 64-bit executable, or 4 bytes for a 32-bit executable).

After these 2 tables is a special "string table". A string is a list of bytes that represent text. It always ends with a zeroed byte (This is called null-termination) to indicate the end of the string. We keep these separate from the code. Typically they are read-only and duplicates are merged into one to save memory. The string table starts with 4 bytes specifying its size, followed by all of its contents, rather than having its size specified by the header.

----

It's worth noting that there is an intermediate format known as an *object file*. This is a partial executable file, it has parts missing. It won't have an entry point, and not all of its symbols have to be associated with a dynamic library.

The object files are then *linked* together to form an executable, and an entry point is specified. This is where the other name for a dynamic library comes from, a *shared object*. A shared object is one that gets linked upon running the file, rather than while building the executable! This allows it to be shared between multiple executables. Well, to be more specific, the text section is shared, but the data sections are not shared.
